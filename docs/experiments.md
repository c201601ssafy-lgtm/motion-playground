## E-01 AI 튜터가 도구 없이 답하고 숫자를 지어냄 (qwen3:8b)

**문제** — 실제 로컬 LLM(qwen3:8b Q4_K_M, Ollama 0.40.2, `think=false`)에 튜터 질문 16개(`evals/tool-call-cases.jsonl`)를 줬더니 일부 질문에 도구를 부르지 않고 답했다. 그중엔 도구 결과에 없는 숫자도 있었다.

**기준 성능** (`evals/reports/tool-calls-ollama-baseline.md`)

| 지표 | 값 |
|---|---|
| 도구 선택률 | 75% |
| 인자 정확도 | 50% |
| 실행 성공률 | 100% |
| 미근거 숫자 답변 비율 | 18.8% |
| 사실 일치율 | 90% |
| 지연 p50 | 6.9 s |

**원인 분석**
- 실패 4건 가운데 3건이 부품 질문("아이들러 기어는 왜 필요해?", "출력축은 무슨 일을 해?", "이건 뭐야?(선택 부품)")이었다. 모델이 일반 상식으로 바로 답해 버렸다.
- "지금 몇 단계야?"는 도구 없이 "2단계"라고 추측했다 → `UNGROUNDED_NUMBER:2`.
- 시스템 프롬프트의 "도구를 호출하라"만으로는 8B 모델이 매번 따르지 않았다.

**개선** (`backend/app/ai/tutor.py`)
1. 프롬프트에 질문 유형 → 도구 대응표를 넣었다(부품 → `get_part_info`, 진행 → `get_assembly_state` 등).
2. **도구 강제 되묻기**: 첫 응답이 도구를 하나도 쓰지 않으면 "답하기 전에 도구를 먼저 호출하라"를 한 번 덧붙여 다시 묻는다(최대 1회).
3. `input_rpm` 설명에 "사용자가 말하지 않으면 30"을 명시했다(모델이 100을 임의로 고른 사례가 있었음).

**재측정** (`evals/reports/tool-calls-ollama.md`)

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| 도구 선택률 | 75% | **94%** |
| 인자 정확도 | 50% | **83%** |
| 미근거 숫자 답변 비율 | 18.8% | **0%** |
| 사실 일치율 | 90% | 90% |
| 지연 p50 / 최대 | 6.9 s / 15.6 s | 7.7 s / 20.1 s |

**결과** — 사실 확인 없는 답변이 사라졌다. 대신 되묻기 때문에 지연이 조금 늘었다. 남은 실패:
- `simulate`("45rpm으로 돌려 봐"): `run_visual_simulation` 대신 `get_mechanism_state`를 호출했다.
- `progress-complete`("조립 다 끝났어?"): 도구는 맞췄지만 답에 "8"(부품 수)을 넣지 않았다. 판정 기준이 엄격해서 생긴 실패다.

다음 단계로 `run_visual_simulation` 설명에 "돌려 봐/작동시켜"를 예시로 넣고, 다시 측정한다.

**후속 개선 (P5-1, 2026-10-11)**
1. `run_visual_simulation` 설명에 "'45rpm으로 돌려 봐', '작동시켜 줘', '돌아가는 거 보여 줘'" 예시를 넣었다. `get_mechanism_state` 설명에는 "값을 묻는 질문용"이라고 구분을 적었다. 시스템 프롬프트 규칙 2에도 같은 대응을 추가했다.
2. 1번 후 재측정에서 `simulate`가 맞는 도구를 골랐다. 하지만 답에 "3", "15"를 넣어 `UNGROUNDED_NUMBER:3,15`가 붙었다. 값은 맞았다(45 ÷ 3 = 15). 시뮬레이션 도구가 rpm을 돌려주지 않아 모델이 직접 계산한 것이다. 그래서 `run_visual_simulation` 결과에 `reduction_ratio`와 기어별 `gears`(방향·rpm)를 넣었다.

| 지표 | P4-5 개선 후 | 설명 보강 | + 시뮬레이션 결과에 rpm |
|---|---|---|---|
| 도구 선택률 | 94% | 100% | **100%** |
| 인자 정확도 | 83% | 100% | **100%** |
| 미근거 숫자 답변 비율 | 0% | 6% | **0%** |
| 사실 일치율 | 90% | 90% | 90% |
| 지연 p50 / 최대 | 7.7 s / 20.1 s | 18.7 s / 28.0 s | 18.7 s / 28.6 s |

- 지연이 늘어난 건 측정 PC가 바뀌어서다. 이번 PC는 RTX 4050 Laptop(VRAM 6GB)이라 qwen3:8b(6.0GB)가 다 올라가지 않는다. `ollama ps` 기준 CPU 30% / GPU 70%로 나뉘어 돈다. 같은 PC에서 측정한 두 열은 서로 비교할 수 있다. P4-5 열과는 비교하면 안 된다.
- 남은 실패는 `progress-complete`("조립 다 끝났어?") 하나다. 도구는 맞췄지만 답에 부품 수 "8"을 쓰지 않았다(판정 기준이 엄격함).

재현(측정 환경: Ollama 0.35.1, qwen3:8b Q4_K_M, RTX 4050 Laptop 6GB): `cd backend && LLM_PROVIDER=ollama uv run python scripts/eval_tool_calls.py --provider ollama`

재현: `cd backend && LLM_PROVIDER=ollama uv run python scripts/eval_tool_calls.py --provider ollama`

## E-02 Mock 튜터 규칙의 오류 질문 인식

**문제** — CI와 데모 백업용 규칙 기반 Mock이 "어떻게 고치면 돼?", "기어가 왜 안 들어가?"를 오류 질문으로 분류하지 못했다.

**기준 성능** — 도구 선택률 88% (16개 중 14개), 사실 일치율 90%. CI 기준(90%) 미달로 `exit 1`.

**원인 분석** — 오류 정규식이 "왜…안 되/작동하지/틀렸"만 다뤘다. "고치", "안 들어가", "안 맞"이 빠져 있었다.

**개선** — `RE_ERROR`에 `안 들어|안 맞|안 끼|어떻게 고|고치|수정`을 추가했다(`backend/app/ai/mock.py`).

**재측정** — 도구 선택률 **100%**, 인자 정확도 100%, 사실 일치율 **100%**, 미근거 숫자 0%.

**결과** — CI가 `--min-selection 0.9`로 회귀를 막는다. 다만 Mock은 평가 케이스에 맞춘 규칙이다. 그래서 일반화 성능 지표로는 쓰지 않는다. 실제 성능은 E-01의 qwen3 값을 본다.

재현: `cd backend && uv run python scripts/eval_tool_calls.py --provider mock --min-selection 0.9`

## E-03 좌표 필터 비교 (합성 녹화)

**문제** — 손 좌표를 그대로 쓰면 3D 부품이 떨린다(spec §7). 필터별 흔들림과 오전환을 비교한다.

**기준 성능** (필터 없음, `evals/reports/gesture-eval.md`, 합성 36클립: 3명 × 조명 3 × 라벨 4)

| 필터 | 확정 구간 위치 표준편차 | 클립당 잘못된 전환 |
|---|---|---|
| 없음 | 0.0223 | 0 |
| EMA (α 0.35) | 0.0196 | 0 |
| One Euro (min 1.0, β 4.48) | **0.0190** | 0 |

**원인 분석**
- 합성 클립에는 의도된 좌우 흔들림(±0.03)이 들어 있다. 그래서 표준편차의 대부분은 손의 실제 이동이다.
- 오전환 0은 상태 머신(최소 3프레임 유지, 150ms 쿨다운, PINCH 히스테리시스) 덕분이다. 다만 합성 잡음이 실제보다 단순하다는 점도 영향을 줬다.
- 프레임·클립 정확도 100%와 판정 지연 66ms(=3프레임 유지 × 33ms)는 합성 데이터라서 나온 값이다. 실제 성능으로 볼 수 없다.

**개선** — 기본 필터를 One Euro로 정했다. 정지 시 흔들림은 가장 작고, `vitest`의 빠른 이동 테스트에서 EMA보다 지연이 작았다(`frontend/tests/gestures.test.ts`).

**재측정 (실제 카메라 경로 점검)** — MediaPipe 공식 샘플 손 사진을 가짜 카메라(y4m)로 2초 녹화해 평가했다. 결과는 56프레임 모두 손 감지, OPEN_PALM 정확, 판정 지연 72ms였다. 브라우저 단계별 지연(GPU, headless Chrome)은 랜드마크 추출 p50 11ms·p95 31ms, 프레임→명령 p95 37ms였다(D-009 목표 50ms·200ms 이내).

**결과 / 남은 일** — 실제 사람 데이터가 없다. 녹화 화면(`#/record`)으로 7명 × 4라벨 × 조명 3 × 10클립(D-008)을 모아 `datasets/gestures/raw/`에 넣고, 같은 스크립트로 다시 측정해야 한다. 이때 사용자 단위 분리(leave-one-subject-out)와 학습 분류기(RandomForest) 비교를 추가한다.

재현: `cd backend && uv run python scripts/eval_gestures.py [녹화.jsonl ...]`

## E-04 서버 기동 직후 첫 튜터 질문 지연 (P5-2)

**문제** — 서버를 띄운 뒤 첫 질문은 Ollama가 그때 모델을 메모리에 올리기 때문에 느리다(P4 측정 PC에서 20~40s). 또 Ollama 기본 `keep_alive`가 5분이라 데모 중 5분 넘게 질문이 없으면 모델이 내려가고, 다음 질문이 다시 느려진다.

**개선** (`backend/app/ai/ollama.py`, `provider.py`, `main.py`)
1. 서버 시작 시 백그라운드 스레드로 `/api/generate`(프롬프트 없음)를 불러 모델만 미리 올린다. 서버 기동은 막지 않는다. 실패하면 경고 로그만 남기고, 첫 질문 때 평소처럼 로딩한다. 끄려면 `OLLAMA_WARMUP=false`.
2. 모든 요청에 `keep_alive`를 넣는다(`OLLAMA_KEEP_ALIVE`, 기본 `30m`).

**측정** — 매 회 `ollama stop qwen3:8b`로 모델을 내리고, uvicorn을 새로 띄운 뒤 "작은 기어는 무슨 역할을 해?"를 두 번 묻는다. 예열을 켠 경우는 모델이 올라온 뒤(사용자가 화면을 여는 동안 끝난다고 가정) 묻는다. 측정 환경: RTX 4050 Laptop 6GB, Ollama 0.35.1, qwen3:8b(CPU 30% / GPU 70%).

| 회차 | 예열 | 서버 응답 가능 | 모델 적재 완료 | 첫 질문 | 두 번째 질문 |
|---|---|---|---|---|---|
| 1 | 끔 | 1.3 s | - | 23.5 s | 16.7 s |
| 1 | 켬 | 0.5 s | 7.7 s | 22.9 s | 20.6 s |
| 2 | 끔 | 1.2 s | - | 27.4 s | 17.2 s |
| 2 | 켬 | 0.6 s | 7.7 s | 18.7 s | 17.4 s |

**결과** — 예열 로그 기준 모델 적재에 6.8~7.1s가 걸렸다. 첫 질문 평균은 25.5s → 20.8s로 약 5s 줄었다. 예열을 켜면 첫 질문이 두 번째 질문과 비슷한 수준이 된다.
- 이 PC에서는 모델 파일이 OS 캐시에 있어 적재 시간이 짧았다. 그래서 줄어든 폭도 작다. 지연의 대부분은 VRAM 부족으로 CPU에 넘어간 층 때문에 느려진 생성 시간(17~20s)이다. 더 줄이려면 VRAM 8GB 이상 GPU를 쓰거나 `qwen3:4b`로 바꿔야 한다(도구 선택률 재측정 필요).
- 회차가 2회뿐이라 흔들림이 크다(두 번째 질문 16.7~20.6s).
- `keep_alive=30m` 효과(5분 넘게 쉰 뒤 질문)는 따로 재지 않았다.

재현: `cd backend && uv run python scripts/measure_first_response.py --runs 2`

## E-05 학습 분류기(RandomForest) vs 규칙 분류기 (P5-8)

**문제** — 규칙 분류기는 손가락 굽힘 각도와 집기 거리에 임계값을 둔 것이다. 학습 분류기가 사람마다 다른 손 모양을 더 잘 잡는지 확인하려 한다(spec §6).

**방법** (`backend/scripts/train_classifier.py`)
- 특징: 손목 원점, 손 크기 1로 정규화한 랜드마크 (x, y) 42개 + 규칙 분류기가 쓰는 손가락 특징 10개(펴짐 5, 접힘 4, 집기 거리).
- 분류기: RandomForest 200그루(`random_state=0`).
- 분리: 사용자 단위(leave-one-subject-out). 같은 사람의 프레임이 학습과 시험에 섞이면 점수가 부풀기 때문이다.
- 손이 감지된 프레임만 비교했다.

**결과** (`evals/reports/classifier-compare.md`, 합성 녹화 36클립 1,056프레임, 피험자 3명)

| 분류기 | Accuracy | Macro F1 |
|---|---|---|
| 규칙 기반 | 100.0% | 1.000 |
| RandomForest | 99.9% | 0.999 |

**해석** — 합성 손은 규칙 분류기와 같은 가정(손가락 굽힘 각도)으로 만들었다. 그래서 규칙이 100%가 나오는 건 당연하고, 이 비교로는 어느 쪽이 나은지 말할 수 없다. 스크립트와 분리 방식이 돌아가는지만 확인한 것이다.

**남은 일** — `#/record`로 7명 × 4라벨 × 조명 3(D-008)을 모아 `datasets/gestures/raw/`에 넣으면 같은 명령으로 다시 잰다. 그때 규칙이 틀리는 사람·조명에서 RF가 나은지, 시계열을 쓰는 1D CNN이 필요한지 판단한다.

재현: `cd backend && uv sync --group ml && uv run python scripts/train_classifier.py`
